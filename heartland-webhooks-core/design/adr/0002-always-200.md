# ADR-0002 — Webhook endpoints always answer HTTP 200

**Status:** Accepted · **Date:** 2026-10-26

## Context

Heartland Retail retries webhook endpoints that return errors and **eventually
disables** an endpoint that keeps failing. A disabled endpoint is a silent,
store-wide automation outage that nobody notices until someone asks why the
notifications stopped.

Meanwhile, plenty of conditions that are "failures" from Clutch's point of view
are not things Heartland can fix by retrying: an unparseable body, a webhook
registered against an unknown tenant path, a bug in a handler.

## Decision

`webhookResponse()` returns `statusCode: 200` unconditionally. Every outcome —
success, ignored, and every class of error — is reported in the JSON body:

```json
{ "status": "ok" | "ignored" | "error", "eventType": "...", "ok": true|false,
  "tenantId": "...", "handler": "...", "reason": "...", "details": { } }
```

`status` is the stable contract field. Failures are additionally logged at
`error` level with the tenant tag, which is the real alerting channel.

The pipeline catches exceptions at both points where they can arise —
`registry.context()` and `invoke()` — specifically to preserve this.

## Consequences

- Heartland never disables a Clutch endpoint, no matter how badly a handler
  misbehaves. This is the property being bought.
- A handler failure cannot take the endpoint down for other tenants sharing the
  same function.
- CloudWatch is the only failure signal, which raises the bar on log quality:
  every error path carries a `reason`, the tenant id, the handler name, and the
  `describe()` fields.
- **Heartland's retry mechanism is given up entirely.** An event lost to a
  transient failure is lost; nothing redelivers it. This is the direct cause of
  [open question 4](../06-open-questions.md) — retry, if it is ever wanted, must
  be built inside Clutch.
- Tests must assert on `body.status`, not on `statusCode`. A test that checks for
  a non-200 is testing the wrong thing.
- An HTTP-level monitor cannot tell a healthy endpoint from a failing one.

## Alternatives considered

**Correct HTTP semantics** — 400 for a bad body, 404 for an unknown tenant, 500
for a handler error. The conventional choice, and it would preserve Heartland's
retries. Rejected because the cost of being wrong is asymmetric: a 4xx for a
genuinely malformed body still counts toward the failure budget that disables the
endpoint, and endpoint disablement is a worse outcome than a lost event.

**200 for client errors, 5xx only for retryable server errors.** The nuanced
middle, and the likely destination if durable retry is ever built. Rejected for
now because it requires confidence about which Heartland failure modes count
toward disablement, and that confidence does not exist. Revisit together with
[open question 4](../06-open-questions.md).
